## Scripts and their lint

The Python tooling is managed with [uv](https://docs.astral.sh/uv/):
`pyproject.toml` pins the lint tools in its `lint` dependency group,
`uv.lock` pins the full tree, and `.python-version` the interpreter. With uv
installed (e.g. `mise use -g uv`), and the shared CI scripts checked out
beside this repository (`git clone https://github.com/Distant-Signal/ci
../ci`; CI uses the commit `.github/workflows/ci.yml` pins):

```sh
uv run python ../ci/scripts/lint-scripts.py         # what CI's scripts-lint job runs
uv run python ../ci/scripts/lint-scripts.py --fix   # apply shfmt/ruff fixes first
uv run python -m unittest discover -s scripts/tests   # the scripts' tests
uv run scripts/sync-core.py --check                  # the site credits from the pinned ds-core release
uv run scripts/sync-api-types.py check               # the frontend's api types and OpenAPI copy vs the pinned api image
uv run scripts/check-sftp-entrypoint.py              # the dev SFTP entrypoint vs ds-deploy's pinned copy
```

Migrations, grants, the Redis ACL and the line catalogue live in
[Distant-Signal/ds-core](https://github.com/Distant-Signal/ds-core): a
change to one is a ds-core pull request and release, then a bump in each
service repository and here (`core-version` and
`uv run scripts/sync-core.py` for the site credits);
Distant-Signal/ds-deploy bumps the chart's `migrate.image` and access
files.

`uv run` creates `.venv/` and installs the `lint` group on first use.
`lint-scripts.py` runs this repository's pinned tools: shellcheck and shfmt
over every `*.sh`, ruff and mypy over `scripts/`, actionlint over the
workflows, hadolint over the Dockerfiles, and Distant-Signal/ci's
`lint-containers.py`.

## Generated API types

The frontend's request and response types come from the api's Rust types,
generated by [ts-rs](https://github.com/Aleph-Alpha/ts-rs) into
`api-types/api.ts` in
[Distant-Signal/ds-api](https://github.com/Distant-Signal/ds-api) (its
README, "The frontend's types and OpenAPI document"; repo-split spec
§5.3). `frontend/lib/api-types.ts` is a byte-for-byte copy, and
`lib/types.ts` names its types for the app. `frontend/lib/openapi-v1.json`
is the same kind of copy of the personal-token API's OpenAPI document,
which the `/developers/api` reference renders at build time.

Both copies come from the api image `frontend/api-image.txt` pins
(`<repository>:build.<run>-<commit>@sha256:<digest>`), which carries them
at `/usr/share/distant-signal/api-types.ts` and
`/usr/share/distant-signal/openapi-v1.json`. `scripts/sync-api-types.py`
reads them, checking the tag, manifest and layer digests against the pin:

```sh
uv run scripts/sync-api-types.py pin --latest   # or a build.<run>-<commit> tag: bump the pin, rewrite both copies
uv run scripts/sync-api-types.py write          # rewrite both copies from the pinned image
uv run scripts/sync-api-types.py check          # CI's repo-checks: the copies match the image
uv run scripts/sync-api-types.py verify-pin --remote https://github.com/Distant-Signal/ds-api   # the image's files are its commit's api-types/
```

So a change the frontend needs lands in ds-api first, additively (a new
optional field or route, with a `docs/api-changelog.md` entry there); once
ds-api's main has built it, the frontend bumps its pin in the pull request
that uses it. CI runs the e2e tests against that image, fails on a
breaking change to the OpenAPI copy, and labels the frontend image with the
pin's build tag, which ds-deploy requires the deployed api to have reached.
Renovate bumps the pin too (renovate.json5); it runs no commands, so run
`write` on its branch.

The api types also export, as `as const` objects, values the web app keeps
its own copy of: `ATTRIBUTION_SOURCES` and `NON_AFFILIATION` (the
personal-token credits) and `USAGE_EVENTS` (the usage-event allowlist).
The frontend's tests (`components/OpenDataAttribution.test.tsx`,
`lib/usageEvents.test.ts`) compare its copies against them. ds-core's
line-catalogue validator states its one website credit the same way, in
its `crates/line-catalogue-validator/site-credits.json` (vendored here by
`sync-core.py`).

Not every route is covered yet: the trains, journeys and trip-plan
responses are; the rest of `lib/types.ts` is still written by hand.

## Dependency and security scans

What fails CI and what only warns:

- `dependency-scan.yml` (OSV-Scanner over `frontend/package-lock.json`
  and `uv.lock`) **blocks** on a finding with
  CVSS >= 9.0 that has a fixed version, and on a scan that produced no valid
  JSON. Every other HIGH/CRITICAL (CVSS >= 7.0) finding **warns**: a
  per-finding annotation and a neutral "security findings (non-blocking)"
  check. The daily scheduled run never blocks on findings; it opens or
  updates a `dependency-vulnerability` issue instead. Time-boxed exceptions
  live in `frontend/osv-scanner.toml`.
- The Rust repositories run cargo-deny themselves (Distant-Signal/ci's
  rust-ci.yml).

## Commit history and old commit SHAs

This repository's history was rewritten once, when it moved to the
Distant-Signal organisation (November 2026): each step of `main` became
one commit, so every commit SHA from before then changed. SHAs cited in
files were updated to the rewritten commits, except in migrations and
their `contract:` headers, which are checksum-locked and keep the
original SHAs.

To resolve an original SHA (from a migration header, an old chart or image
tag, a deploy record or a commit link), look it up in the migration
ledger. The ledger is owner-only, so outside readers can't resolve old
SHAs apart from old pull request pages, which still show the original
commits.
